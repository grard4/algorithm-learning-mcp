# Schema 演进策略（设计，不是已实现功能）

第二轮 A06 结论：DESIGN_DECISION。当前 core-v1 校验能够识别已部署账本、拒绝未知版本/checksum及结构漂移，原子初始化失败可回滚。5项既有迁移测试通过；本轮不修改 migrations.py、SQL文件、迁移历史或用户数据库。

## 当前约束

core-v1 的 checksum 来自三个现有 SQL 文件的完整文本。文件的空格、注释改变也会改变 checksum，因而已应用的迁移材料应视为不可变。数据库账本一致与结构核对可以发现意外改动，不是数字签名，也不能防止拥有源码和数据库写权限的人同时修改二者。未知自定义旧库必须单独评估，不能伪造 checksum 强行接纳。

## 未来实施路径

1. 固定现有 v1 SQL 的原始字节及来源提交，保留无账本的已知旧结构接纳路径。不要直接编辑旧 Schema 文件来“升级”。
2. 新增有序且不可变的迁移清单：core-v1、core-v2、core-v3，各含独立文件和 checksum。账本须是清单的连续前缀；未知、缺项、重复或被改写的历史版本一律停止。
3. 在维护窗口中备份数据库、WAL关联状态和归档，验证备份完整性与恢复可用性，在副本先执行。CLI当前在线备份能力可作为起点，不能用文件复制代替正在写入的SQLite一致备份。
4. 升级程序在同一连接取得写锁，按确定顺序执行尚未应用的版本。每个版本的结构/数据变更与账本更新同一事务提交；任何失败回滚该版本。多版本升级中已提交版本保留，重启从账本继续，不能重放已经提交的数据转换。
5. 新库也从相同清单构建；若引入最新快照，需测试它与按序迁移所得的结构、索引、触发器及数据约束等价。R3通知Schema的演进须与其健康检查同时规划。
6. 只有新程序能读取新账本时才激活服务；旧程序遇到高版本应拒绝启动。破坏性变更不提供未经验证的逆迁移，回滚采用完整备份恢复到新目标，再切换配置；不要只回退源码并继续写新库。

## 每个未来版本必须通过的测试

空库、完整 v1、已识别旧库、含真实形状合成数据的逐版本升级；重复启动无变更；每条DDL/数据转换边界失败与进程退出；事务回滚、重试、并发启动、未知/篡改账本拒绝；升级前后主外键、行数、内容、索引、触发器、同步游标和通知epoch；备份恢复后 integrity_check 与 foreign_key_check。

只有上述实现与证据完成后才新增真实 core-v2。当前 core-v1 文件改动导致拒绝属于预期防护，不通过忽略 checksum 或自动覆写账本消除告警。
